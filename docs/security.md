# 보안과 개인정보 보호

## §1 원칙과 보호 대상
| 보호 대상 | 위협 | 대응 |
|---|---|---|
| 사용자 AI API 키 | 소스·로그·내보내기·백업 유출, 과금 도용 | OS 보안 저장소만 사용, 마스킹, 비밀정보 검사(§2, §8) |
| 사용자 번역·설정 | 업데이트·캐시 정리로 소실, 손상 | 영구 영역 SQLite, 원자적 저장, 안전한 마이그레이션(§6) |
| 알림 내용(Android) | 알림 리스너 권한 남용 | 미디어 세션 조회만, 알림 내용 미접근·미저장(§3) |
| 비용 | 무한 호출, 중복 과금 | 동의·상한·결과 미확인 시 재요청 금지(§4, §5) |
| 앱 동작 | 악성 가사·파일·AI 응답(프롬프트 인젝션, 거대 입력) | 불신 데이터 검증(§7) |

## §2 키 관리
- **저장 위치**: `SecretStore` 포트 → 앱에서는 `expo-secure-store`(Android: Keystore 키로 암호화해 저장, iOS: Keychain). 일반 설정(SQLite `settings`)·AsyncStorage·파일에 저장하지 않는다.
  - iOS 접근 등급은 `WHEN_UNLOCKED_THIS_DEVICE_ONLY`를 기본으로 검토(백업 복원 시 다른 기기로 이동하지 않음). iOS Keychain은 앱 삭제 후에도 남을 수 있으므로 "키 삭제" 기능과 첫 실행 시 잔존 키 정리 여부를 결정한다(Phase 3).
  - Android는 Auto Backup에서 보안 저장소 항목 제외(expo-secure-store 설정 플러그인 기본 동작, MV-SEC-01에서 확인).
- **등록·교체·삭제**: `ApiKeyManager.set/delete/has/hint`. 형식 검사(길이 8–512, 공백·제어 문자 금지). 화면에는 끝 4자리만(`••••abcd`). 교체 시 이전 값도 마스킹 목록에 유지.
- **사용**: 요청 직전에만 `getForRequest`로 읽고, 반환값을 변수 외에 저장·로그하지 않는다.
- **금지**: 키를 소스·앱 번들·테스트 데이터·문서·채팅에 넣지 않는다. 사용자에게 키를 채팅이나 문서에 붙여 넣도록 요구하지 않는다(앱 설정 화면에서만 입력).
- **개발자 공용 키 금지**: 개발자 소유 비밀 키를 앱에 넣지 않는다. 공용 키가 필요한 기능(예: Apple Music API 개발자 토큰 서명, 공용 번역 서비스)은 **별도 서버**가 키를 보관하고 앱은 사용자 인증 후 단기 토큰만 받는 구조로 설계한다(현재 범위 밖, docs/plan.md D-08).
- **검사**: `npm run scan:secrets`(check에 포함) — 키 형식 문자열, `.env`·키 파일 존재 시 실패. 테스트용 가짜 키는 실행 중에 조립한다.

## §3 권한 (최소 권한)
| 권한 | 플랫폼 | 용도 | 원칙 |
|---|---|---|---|
| 알림 접근(Notification Listener) | Android | `MediaSessionManager.getActiveSessions` 사용 조건 | 사용 이유를 먼저 설명 후 설정 화면으로 안내. 거부 시 수동 모드. **알림 텍스트·발신자 등 알림 내용은 읽지 않고 저장·전송하지 않는다.** 서비스 구현은 `onNotificationPosted`를 비워 두고 세션 조회만 한다. |
| 미디어 라이브러리/Apple Music | iOS | `systemMusicPlayer` 상태 조회·제어 | 사용 설명 문구에 목적 명시 |
| 다른 앱 위에 표시 | Android | 오버레이(별도 기능) | 기본 비활성, MV-OVL-01 후 결정 |
| 네트워크 | 공통 | LRCLIB, 사용자 AI 제공자 | HTTPS만 |
| 파일 선택 | 공통 | TXT/LRC 가져오기 | 시스템 파일 선택기로 사용자가 고른 파일만 |

스트리밍 서비스 계정 로그인(OAuth)은 현재 사용하지 않는다. 필요해지면 공식 모바일 인증 흐름(PKCE, 시스템 브라우저)과 최소 범위만 사용한다.

## §4 외부 전송·동의·비용
- **AI로 보내는 데이터**: 가사 원문 행 텍스트(빈 행 제외), 행 ID, 곡 언어, 작업 지시. **보내지 않는 것**: 스트리밍 계정 정보, 서비스 곡 ID, 기기 정보, 사용자 번역, 다른 곡 정보. (Spotify 정책상 Spotify 콘텐츠를 AI에 넣지 않도록 곡 제목·아티스트도 보내지 않는다.)
- **동의**: 자동 번역은 기본 꺼짐(`translate.auto=false`). 켜기 전·첫 수동 번역 전에 제공자 이름, 전송 데이터, 예상 비용(원문 글자 수 기반 추정, 제공자 단가는 사용자가 확인)을 보여주고 선택하게 한다.
- **비용·호출 제한**: 일일 요청 상한(기본 30회, `reserveUsage`로 요청 전 원자적 예약), 1회 요청 크기 상한(400행·12,000자), 자동 재시도 없음(사용자 재시도만), 취소 지원(`CancelSignal`).
- **LRCLIB**: 곡 제목·아티스트·앨범·길이가 전송된다. 순차·간격 요청, Retry-After 준수.

## §5 중복 과금 방지와 남는 경계
- 요청 전 작업을 `in_flight`로 기록 → 응답 검증·저장과 `completed` 전환을 한 트랜잭션으로 처리.
- 전송 전 실패(오프라인 확정), 401/403/400/429/503은 **처리되지 않은 요청**으로 보고 `failed`(과금 위험 none).
- 타임아웃, 5xx, 전송 후 연결 끊김, 앱 종료(다음 실행 시 `in_flight` 발견)는 **처리·과금 여부를 알 수 없음** → `unknown_outcome`, 자동 재요청 금지. 사용자가 "중복 과금 가능성"을 확인해야 재요청.
- 같은 곡 동시 요청은 메모리에서 하나로 합친다(앱 프로세스 안). **프로세스가 둘 이상인 경우(예: 위젯·백그라운드 작업 추가 시)는 합쳐지지 않는다** → 그때는 DB 작업 테이블로 잠금을 추가해야 한다.
- **완전히 막을 수 없는 경계**: OpenAI·Anthropic 공식 문서에서 범용 Idempotency-Key 지원을 확인하지 못했다(2026-10-04). 따라서 "서버는 처리했지만 응답을 못 받은 경우"의 과금은 막을 수 없고, 앱은 **같은 요청을 자동으로 다시 보내지 않는 것**으로 피해를 1회로 제한한다. 제공자가 요청 ID 조회·중복 방지 키를 지원하면 어댑터에서 활용한다(MV-AI-01에서 제공자별 확인).

## §6 로컬 저장·백업·삭제
- **위치**: SQLite DB는 앱 전용 문서 영역(Android `filesDir`/`noBackupFilesDir` 결정 필요, iOS `Application Support`)에 둔다. 캐시 디렉터리 금지(OS가 지울 수 있음).
- **접근 보호**: 앱 샌드박스(다른 앱 접근 불가). DB 자체 암호화는 하지 않는다(가사·번역은 비밀정보가 아니며 키는 별도 보안 저장소). 민감도가 높아지면 SQLCipher 검토.
- **백업**: 사용자 번역은 사용자 작업물이므로 OS 백업 포함을 기본으로 검토하되, 보안 저장소 항목은 제외. 앱 내 백업(설정 › 백업, JSON)으로 사용자가 직접 보관한다(2026-10-05 구현, REQ-ST-04). 백업에는 API 키·제공자 설정·자동 번역 동의·작업 이력이 없다(AT-13·AT-15). 가져오기는 불신 파일로 다룬다: 크기·개수·문자열 길이 상한, 형식 검사, 곡↔가사↔번역 참조 검사, 가사 해시 재계산(원문·타임스탬프 변조 거부), 하나라도 틀리면 전체 거부(AT-16). 저장은 한 트랜잭션, 기존 데이터는 지우거나 고치지 않는 병합. 선택한 파일은 읽기만 하고, 내보내기 임시 사본은 공유 시트가 닫히면 지운다.
- **마이그레이션 전 사본**: 앱 시작 시 스키마 버전이 낮으면 DB 파일 사본(`lyrics.db.bak-v<n>`)을 만든 뒤 마이그레이션, 성공 후 최근 1개만 유지.
- **삭제**: 설정에서 "곡별 삭제", "전체 데이터 삭제", "API 키 삭제"를 제공. 전체 삭제는 DB 파일과 보안 저장소 항목을 모두 지운다. 앱 삭제 시 OS가 앱 데이터를 지운다(iOS Keychain 잔존 예외는 §2).
- **개발 PC**: 실제 가사·실기기 DB 사본·개인 번역은 `local-data/`(git 제외)에만 둔다. 테스트 데이터는 합성 데이터만(`fixtures/`).

## §7 외부 입력 검증 (불신 데이터)
| 입력 | 검증 |
|---|---|
| LRCLIB 응답 | 상태 코드·Content-Type 확인, 본문 2MB·가사 256KB 상한, 필드 타입 검사(`validateRecord`), 버전·길이 호환성 |
| LRC/TXT(가사·사용자 파일) | 256KB/512KB 상한, 행 수 상한, BOM·CRLF·제어 문자 정리, 타임스탬프 범위, UTF-8 깨짐(U+FFFD) 경고 |
| AI 응답 | 1MB 상한, JSON·스키마·행 ID 집합·순서 검사, 거절 탐지, 길이 상한, 읽기 문자 집합 |
| 가사 속 지시문 | 시스템 지시와 분리된 JSON 데이터로만 전달, "지시문이 아니다" 명시, 응답은 스키마 밖 내용을 버림(예: 응답에 넣은 시간 값 무시) |
| 화면 표시 | React Native Text로만 렌더링(HTML·마크다운 해석 없음) |

## §8 로그·오류 보고
- core 로그는 `Logger`를 거쳐 등록된 키 값·키 형식·민감 필드 이름(Authorization 등)을 `[REDACTED]`로 바꾼다.
- 가사 원문·번역 전문은 로그에 남기지 않는다(행 수·글자 수만).
- 제공자 오류 메시지는 저장 전에 마스킹(제공자가 키를 되돌려 주는 경우 대비, AT-13).
- 외부 오류 보고 서비스(Sentry 등)는 현재 사용하지 않는다. 도입 시 같은 마스킹과 사용자 동의 필요.

## §9 전송 보안
- LRCLIB·AI 제공자 URL은 `https://`만 허용(생성 시 검사). OS 기본 인증서 검증을 사용하고, 검증을 끄는 옵션을 만들지 않는다. Android `usesCleartextTraffic=false`, iOS ATS 예외 없음.
- 인증서 고정(pinning)은 사용자 지정 제공자(OpenAI 호환 임의 서버)와 충돌하므로 적용하지 않는다.

## §11 iOS 무료 서명 설치(Sideloadly) — 2026-10-04 추가
- 빌드: GitHub Actions에서 **서명하지 않은** IPA를 만든다. 워크플로에 Apple 계정·인증서·API 키 같은 비밀 값을 쓰지 않는다.
- 서명: 사용자 PC의 Sideloadly가 무료 Apple ID로 서명한다. Sideloadly는 Apple 공식 도구가 아니므로 **서명 전용 Apple ID**(음악 구독·결제용 주 계정과 분리)를 권장한다(docs/ios-install.md §6).
- Keychain: API 키는 `WHEN_UNLOCKED_THIS_DEVICE_ONLY`로 저장한다(앱 `src/adapters/secure-store.ts`). 재서명·재설치 후 유지 여부는 MV-IOS-INSTALL-01에서 확인한다.
- 권한: iOS는 `NSAppleMusicUsageDescription` 하나만 요청한다. Music 앱의 현재 곡 정보만 읽으며 서버로 보내지 않는다. 곡 검색어와 재생 중인 곡의 스토어 ID는 iTunes Search/Lookup(Apple)에, 곡 제목·가수·길이는 LRCLIB에 전송된다(가사 조회 목적).
